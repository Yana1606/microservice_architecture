# Турнир математических игр

Учебный проект на C# и ASP.NET Core, моделирующий проведение математического турнира. Система разделена на три основных микросервиса: управление турниром, обработку результатов и формирование итоговой таблицы. Отдельный имитатор воспроизводит события внешних сервисов команд и проверки решений.

Веб-интерфейс «Математическая арена» позволяет создавать и настраивать турниры, регистрировать команды, запускать игры и наблюдать за результатами.

## Возможности

- Создание турнира, настройка регламента и игр.
- Регистрация команд с проверкой состава.
- Управление жизненным циклом турнира и отдельных игр.
- Подготовка игры через Saga с резервированием ресурсов и компенсацией при отказе.
- Приём привязок решений и вердиктов через событийные контракты.
- Расчёт баллов, игровых мест и турнирных очков.
- Формирование публичной таблицы и обновление через Server-Sent Events.
- Transactional Outbox/Inbox, идемпотентность, повторная доставка и Dead Letter Queue.
- Сохранение состояния и восстановление после перезапуска.
- Учебные сценарии eventual consistency, ограниченного детерминизма и 2PC.
- Автоматические тесты и сценарии проверки лабораторной работы.

## Архитектура

| Процесс | Ответственность | Порт по умолчанию |
|---|---|---:|
| `tournament` | Турниры, команды, игры, регламент, сроки и Saga подготовки | 5101 |
| `scores` | Матрица результатов, применение вердиктов, публичная таблица | 5102 |
| `results` | Игровые места, турнирные очки, итоги и победители | 5103 |
| `simulator` | Тестовая имитация событий внешних сервисов и резервирования бланков | 5104 |

Каждый процесс использует собственную SQLite-базу. Сервисы обмениваются событиями через HTTP и не обращаются напрямую к базам друг друга.

`simulator` — вспомогательный тестовый компонент. Он не заменяет полноценные сервисы команд (`team`) и проверки (`checking`).

## Технологии

- C# 12 и .NET 8.
- ASP.NET Core Minimal API.
- SQLite и `Microsoft.Data.Sqlite`.
- HTTP/JSON и событийные контракты.
- Transactional Outbox/Inbox.
- Saga и компенсирующие действия.
- `IMemoryCache` для публичных снимков.
- Server-Sent Events для обновления таблицы.
- HTML, CSS и JavaScript для пользовательского интерфейса.
- xUnit для автоматических тестов.
- Python для вспомогательных лабораторных сценариев.
- Docker Compose и GitHub Actions для конфигурации запуска и CI.

## Требования

Для обычной сборки и запуска необходимы:

- .NET SDK 8;
- Windows PowerShell или совместимая среда для запуска скриптов;
- доступ к NuGet при первом восстановлении пакетов;
- современный браузер.

Python требуется для запуска дополнительных лабораторных сценариев. Для браузерной автоматизации дополнительно нужны Chrome или Edge и пакет `websocket-client`.

Docker требуется только для контейнерного запуска. Если Docker Engine недоступен, можно использовать обычный запуск через PowerShell.

## Сборка и тестирование

Команды выполняются из корневого каталога репозитория.

```powershell
dotnet restore MathTournament.sln
dotnet build MathTournament.sln --no-restore
dotnet test tests/Tests.csproj
```

Для сохранения результатов тестирования в формате TRX:

```powershell
dotnet test tests/Tests.csproj `
  --logger "trx;LogFileName=tests.trx" `
  --results-directory test-results
```

## Запуск

Обычный запуск:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/start.ps1
```

После запуска откройте:

```text
http://localhost:5102
```

Запуск на альтернативном диапазоне портов:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/start.ps1 -BasePort 7101
```

В этом режиме веб-интерфейс доступен по адресу:

```text
http://localhost:7102
```

Остановка процессов:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/stop.ps1
```

## Демонстрация

В веб-интерфейсе выберите «Демо» и запустите демонстрацию. Сценарий показывает две команды, две последовательные игры, изменение статусов решений и итоговые результаты.

В демонстрационном сценарии используются входные вердикты имитатора. Расчёт результатов и формирование итогов выполняют соответствующие сервисы проекта.

Ожидаемый демонстрационный результат, описанный в материалах лабораторной проверки:

```text
Интеграл: 200
Квадрат мысли: 196
```

## Дополнительные лабораторные сценарии

### Saga и компенсация

```powershell
python scripts/lab-demo.py saga --base-port 7101
```

Сценарий демонстрирует резервирование ресурсов, отказ одного из участников подготовки, компенсацию и повторную попытку запуска игры.

### CAP и eventual consistency

```powershell
python scripts/lab-demo.py cap --base-port 7101
```

Сценарий временно приостанавливает доставку событий, показывает чтение последнего публичного снимка и последующую сходимость результатов после восстановления связи.

### Перезапуск координатора Saga

```powershell
python scripts/check-lab.py
```

Сценарий использует отдельные процессы и базы данных, проверяет восстановление координатора после принудительного завершения и продолжение компенсации.

### Ограниченный детерминизм

```powershell
dotnet test tests/Tests.csproj `
  --filter FullyQualifiedName~DeterminismTests
```

Проверяются допустимые порядки доставки фиксированного набора событий, дубликаты и совпадение конечной публичной проекции.

### Учебная модель 2PC

```powershell
dotnet run --project src/TwoPhaseLab/TwoPhaseLab.csproj
```

Отдельный консольный пример показывает Commit, Abort и восстановление после недоступности координатора. Он не участвует в основном жизненном цикле турнира.

## Надёжность и согласованность

Сервисы сохраняют изменения в собственных SQLite-базах. Для событийной интеграции используется Outbox/Inbox. Повторная доставка допускается, поэтому обработчики должны быть идемпотентными.

Временные ошибки доставки повторяются с задержкой. Постоянные HTTP 4xx, кроме 408 и 429, переводятся в Dead Letter Queue. После устранения причины организатор может вручную вернуть сообщение в очередь.

Публичная таблица строится как отдельная проекция. GET и SSE используют общий механизм кеширования снимков. Кеш не является источником истины: версия снимка сохраняется в SQLite.

## Ограничения проекта

- `team` и `checking` не реализованы как самостоятельные полноценные микросервисы; их поведение в демонстрации воспроизводит `simulator`.
- SQLite и единый JSON-снимок состояния рассчитаны на небольшой учебный турнир и один экземпляр каждой роли.
- Учебная модель 2PC не является XA/DTC и не обеспечивает распределённую транзакцию SQLite.
- CAP-сценарий моделирует задержку доставки на уровне Outbox, а не физическое отключение сети.
- Нет промышленной системы аутентификации, OIDC, TLS и многоузлового масштабирования.
- Реальная проверка QR, приём фотографий и работа судейского интерфейса находятся за пределами реализованных сервисов.

Подробные границы и допущения приведены в `docs/architecture.md` и `docs/integration.md`.

## Проверка истории коммитов

Проверка истории:

```powershell
python scripts/check-commits.py
```

Проверка подготовленных к коммиту изменений:

```powershell
python scripts/check-commits.py --staged
```

Скрипт контролирует ограничение на количество изменённых файлов в каждом коммите и исключение генерируемых артефактов.
