# Сценарий защиты лабораторной

## Подготовка

Все команды выполняются из корневого каталога репозитория.

В примерах используется альтернативный диапазон портов 7101–7104. При обычном запуске без `-BasePort 7101` интерфейс открывается на `http://localhost:5102`.

Перед демонстрацией рекомендуется выполнить сборку и тесты:

```powershell
dotnet restore MathTournament.sln
dotnet build MathTournament.sln --no-restore
dotnet test tests/Tests.csproj --no-build `
  --logger "trx;LogFileName=tests.trx" `
  --results-directory test-results
```

Запустить сервисы:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/start.ps1 -BasePort 7101
```

Открыть `http://localhost:7102`.

## 1. Обычный турнир

В интерфейсе выбрать **«Демо» → «Запустить демонстрацию»**.

Показать:

- две зарегистрированные команды;
- две последовательные игры;
- изменение состояний решений;
- четыре цвета вердиктов;
- обновление публичной таблицы;
- завершение турнира.

Ожидаемый демонстрационный результат:

| Команда | Итог |
|---|---:|
| Интеграл | 200 |
| Квадрат мысли | 196 |

Важное пояснение: имитатор создаёт входные события и вердикты, а расчёт результатов выполняют сервисы `scores` и `results`. Это не означает, что в проекте реализованы полноценные сервисы `team` и `checking`.

Подготовка игры проходит через Saga. Сроки решений и апелляций начинают отсчитываться после успешного завершения подготовки.

## 2. Saga с реальной компенсацией

Запустить:

```powershell
python scripts/lab-demo.py saga --base-port 7101
```

Ожидается успешное завершение сценария с сообщением `PASS Saga...`.

Сценарий показывает:

1. Создание отдельного тестового турнира.
2. Резервирование таблицы в сервисе баллов.
3. Отказ имитатора при резервировании бланков.
4. Запуск компенсирующих команд.
5. Состояние `Compensating`, пока не получены оба подтверждения освобождения.
6. Возврат игры в `Configured`.
7. Повторную попытку с новым `attemptId`.
8. Успешный запуск новой попытки.

Пока компенсация не завершена, повторный старт запрещён. Физический резерв таблицы после освобождения имеет состояние `Released`. Публичные результаты не должны создаваться до `GameStarted`.

Открыть раздел «Игры» и выбрать созданный турнир с идентификатором `saga-...`.

Дополнительно можно показать защищённую диагностику `/internal/diagnostics` сервисов турнира и баллов.

### Ручная демонстрация

1. Войти как организатор.
2. Создать и настроить турнир.
3. Зарегистрировать команды от имени капитанов.
4. Начать турнир.
5. В разделе «Игры» включить учебный отказ бланков.
6. Попытаться начать игру.
7. Показать компенсацию резервов.
8. После завершения компенсации повторить запуск.

### Восстановление после перезапуска координатора

```powershell
python scripts/check-lab.py
```

Скрипт запускает собственные процессы на портах 7201–7204 и использует отдельные базы в `test-results`. Он принудительно завершает координатор во время Saga, запускает его снова и проверяет продолжение компенсации и повторную попытку.

Проверка не останавливает основной демонстрационный турнир. Каждый сервис работает со своей базой; взаимодействие между ними идёт через API.

## 3. CAP и eventual consistency

Запустить:

```powershell
python scripts/lab-demo.py cap --base-port 7101
```

Сценарий временно приостанавливает часть доставки событий на стороне отправителя.

Показать следующие результаты:

- GET таблицы и SSE продолжают отдавать последний известный публичный снимок.
- Турнир сохраняет закрытие приёмов по абсолютным срокам, даже если уведомления ещё находятся в Outbox.
- После восстановления первого направления баллы и итоги постепенно сходятся.
- Пока подтверждённый итог не дошёл до сервиса турнира, запуск следующей игры блокируется ответом 409.
- После восстановления оставшейся связи следующая игра становится доступной.
- Итоговая таблица сходится к 200:196 без повторного начисления очков.

Не следует утверждать, что весь проект является AP или CP. Демонстрируется компромисс конкретных операций: доступность чтения последней проекции и отказ от бизнес-перехода без подтверждённого результата.

Сценарий показывает eventual consistency, но не является формальным доказательством CAP.

## 4. Кеширование

В конце CAP-сценария выполнить повторные GET-запросы и чтение SSE.

В защищённой диагностике сервиса баллов `/internal/diagnostics` показать:

- `cache.hits`;
- `cache.misses`;
- `ttlSeconds`.

Ожидаемый TTL — 10 секунд.

Объяснение:

1. Публичный снимок и его версия сохраняются в SQLite.
2. Изменение снимка выполняется в транзакции.
3. После `COMMIT` кеш инвалидируется.
4. При чтении проверяется сохранённая версия.
5. GET и SSE используют один механизм кеширования.
6. Разные турниры имеют отдельные ключи.

Проверка версии нужна, в частности, для обнаружения изменений, внесённых другим экземпляром `Store`. Поэтому кеширование не устраняет все обращения к SQLite: версия проверяется при чтении.

Тесты отдельно проверяют изменение после вердикта, в том числе при нулевых баллах и изменении только статуса, откат, параллельные чтения и изоляцию разных турниров.

## 5. Ограниченный детерминизм

Запустить:

```powershell
dotnet test tests/Tests.csproj `
  --filter FullyQualifiedName~DeterminismTests
```

Показать тесты `DeterminismTests`.

В тестах используются фиксированные:

- время;
- входные идентификаторы;
- бизнес-факты;
- конечные манифесты.

Проверяются 32 порядка доставки, дубликаты, вердикты раньше привязок и событие о победителе раньше части итогов.

Сравнивается конечная публичная проекция:

- баллы;
- статусы;
- места;
- турнирные очки;
- завершение турнира.

Промежуточные снимки, технические ID исходящих сообщений и аудит не обязаны совпадать.

Гарантия действует при одинаковых непротиворечивых фактах, корректных конечных манифестах, идемпотентности и детерминированной формуле расчёта.

## 6. Учебная модель 2PC

Запустить:

```powershell
dotnet run --project src/TwoPhaseLab/TwoPhaseLab.csproj
```

Ожидаемые сценарии:

| Сценарий | Решение | Состояние участников | Балансы |
|---|---|---|---|
| Commit | Commit сохранён до отправки | Committed / Committed | 90 / 90 |
| Abort | Один участник отказал | Aborted / Aborted | 100 / 100 |
| Recovery | Координатор восстановлен после Prepare | сначала Prepared, затем Committed | сначала 100 / 100, затем 90 / 90 |

Объяснение:

Это учебная модель протокола на прикладных резервированиях SQLite. Это не XA/DTC и не распределённая транзакция самой SQLite.

Координатор и два участника используют отдельные файлы баз данных. Вызовы выполняются в отдельном консольном примере. Недоступность канала решения моделируется явно.

После Prepare участник сохраняет резерв и не выбирает Abort самостоятельно по тайм-ауту. После восстановления он повторно читает сохранённое решение координатора.

Пример не подключён к основному жизненному циклу турнира.

Отличие от Saga: Saga может сначала зафиксировать локальный резерв, а затем компенсировать его отдельной транзакцией. В модели 2PC окончательное списание не выполняется до Commit, а участник после Prepare может ожидать решения координатора.

## 7. Восстановление доставки Outbox

Объяснить разделение ошибок:

| Ошибка | Поведение |
|---|---|
| HTTP 400, 401, 403, 404 и другие постоянные 4xx | Dead Letter Queue |
| HTTP 408 | Повтор |
| HTTP 429 | Повтор |
| HTTP 5xx | Повтор |
| Сетевая ошибка или timeout | Повтор |

Постоянная ошибка не должна бесконечно удерживать очередь получателя. После помещения события в Dead Letter Dispatcher продолжает обработку следующих событий этого получателя.

Под организатором показать:

```text
GET /internal/outbox/dead-letter
```

После устранения причины сообщение можно вернуть в очередь:

```text
POST /internal/outbox/dead-letter/{eventId}/{destination}/retry
```

В диагностике `/internal/diagnostics` показать `outboxDeadLetter`.

Тесты `ReliabilityTests` проверяют постоянную ошибку 400 без блокировки следующего события, повтор для 503, сохранение dead-letter после перезапуска и ручное восстановление.

## 8. Проверка коммитов и остановка

Проверить историю:

```powershell
python scripts/check-commits.py
```

Перед созданием следующего коммита:

```powershell
python scripts/check-commits.py --staged
```

Остановить процессы:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/stop.ps1
```

Лимит составляет 50 изменённых файлов в каждом коммите, а не 50 файлов во всём проекте.

## 9. Требования к демонстрационной машине

- .NET SDK 8.
- Современный браузер.
- Python — только для дополнительных сценариев.
- Chrome или Edge и `websocket-client` — для браузерной автоматизации.
- Интернет — при первом восстановлении NuGet.
- Docker Engine — только для контейнерного запуска.

Для отключения лабораторных управляющих сценариев используется параметр `-DisableLabDemos`.

При прямом запуске Host без `ENABLE_LAB_DEMOS=1` управляющие лабораторные маршруты должны возвращать 404.

## 10. Что важно подчеркнуть на защите

1. У каждого сервиса собственная база данных.
2. Межсервисное взаимодействие выполняется через события и HTTP.
3. Outbox/Inbox обеспечивают сохранение и повторную доставку сообщений.
4. Идемпотентность защищает от повторного применения событий.
5. Saga компенсирует уже выполненные локальные действия при неудачной подготовке.
6. Итоги нельзя финализировать без полных манифестов решений и проверок.
7. Кеш хранит публичную проекцию, но не является источником истины.
8. `simulator` имитирует внешние сервисы, а не заменяет их полноценную реализацию.
9. 2PC — самостоятельный учебный пример, а не часть основной системы.
