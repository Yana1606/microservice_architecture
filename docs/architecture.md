Существенные связи доски: GameStarted → выдача бланков **и** инициализация матрицы; три первичных вердикта (включая старшего) → один обработчик результата; рассмотренная апелляция → замена результата → готовность итогов; закрытие каждого приёма → готовность; GameFinalized → возможность следующей игры **и** начисление очков; WinnerDetermined → завершение турнира. Эти связи реализованы, а не только порядок карточек слева направо.

## Агрегаты и состояния

Tournament включает регистрации и упорядоченные Game: Draft → Registration → Running → Completed. Game: Configured → Running → Completed; SolutionsClosed и AppealsClosed — независимые монотонные флаги, UTC-сроки сохраняются при старте. ScoreGame содержит Cells[team][task], неизменяемые Binding и Verdict, манифесты завершения. Cell: NotSubmitted → Correct/Incorrect; Incorrect → AppealUpheld/AppealRejected. GameResult хранится один раз по `(tournament,game)`. Сумма турнира всегда вычисляется из уникальных вкладов игр; операции «прибавить ещё раз» нет.

Три отдельно запускаемых процесса используют общий исполняемый Host с выбранной ролью SERVICE. Роль ограничивает маршруты REST и допустимые события; БД и outbox независимы. Общая библиотека содержит DTO, чистые обработчики и инфраструктуру; прямого доступа к чужой БД нет.

## Хранение и доставка

SQLite WAL; миграция 001 применяется идемпотентно при запуске. Для небольшого турнира состояние сервиса хранится одним JSON-снимком в SQL-строке. BEGIN IMMEDIATE сериализует изменения между процессами; REST дополнительно требует If-Match с Revision турнира. Гонка двух команд на одной версии даёт один успех и один revision_conflict. Состояние, receipts/inbox, pending, quarantine, outbox и результат команды фиксируются одной транзакцией. Ошибка до COMMIT откатывает всё.

Idempotency-Key обязателен для изменяющих REST-запросов; повтор того же запроса возвращает сохранённый ответ, повтор ключа с другим содержимым отклоняется. Для событий сохраняется исходный конверт; одинаковый event ID с другим содержимым отклоняется. Семантический ключ вердикта `(anonymousId,revision)` защищает от двойного начисления даже с новым event ID.

HTTP-доставка at least once: строка outbox отмечается sent только после успешного ответа. Потеря ответа после COMMIT получателя приводит к безопасному повтору. Ошибки доставки сохраняют attempts/last_error; очередная попытка в следующем цикле. Pending сообщения с неизвестным турниром, не начатой игрой, неизвестной связью или недоставленным первичным вердиктом сохраняются и повторно рассматриваются при каждом событии и после перезапуска. Конфликтующие предметные события попадают в quarantine; это видно в защищённой диагностике. Автоматического удаления таких событий нет.

Tick проверяет сохранённые UTC-сроки каждые 250 мс, при перезапуске закрывает просроченные приёмы. Получатели team/checking должны проверять сам абсолютный срок, а не ждать доставки уведомления закрытия. Уведомление может задержаться. Работа фонового цикла доставки может увеличить задержку закрытия, но не продлевает право отправки.

## Барьер итогов

Одного события «нет активных проверок» недостаточно: оно может обогнать вердикт. TeamSealed после закрытия решений содержит полный набор anonymousId принятых решений. ChecksSealed после закрытия обоих приёмов содержит полный набор **event ID всех** первичных и апелляционных вердиктов. Это контракт конечности потока, который внешний checking выдаёт только после завершения всех назначений, отказов и перепроверок, согласовав полный набор решений с team.

ScoresReady публикуется только когда: оба закрытия доставлены; все Binding из TeamSealed есть и лишних нет; каждому решению соответствует первичный вердикт; все и только вердикты из ChecksSealed применены; нет pending и quarantine по игре. Апелляционный вердикт revision=2 ждёт revision=1. Пустая игра разрешена только при двух явных пустых манифестах. Приём итогов results дополнительно ждёт оба закрытия и проверяет полный набор команд. Барьер является доверенным утверждением внешних сервисов; ранний или ложный seal нарушает их контракт. Сообщения сверх финального seal не меняют запечатанный результат, а становятся инцидентом интеграции.

## Решения по отсутствующим правилам

Пользователь явно разрешил придумать правила в ответе на уточняющий вопрос. Выбраны: `баллы = стоимость исхода × множитель бланка`; обычный ×1, усиленный ×1.5, рискованный ×2; демо верно=10, неверно=0. Сами стоимости и множители обязательны в GameConfig, нет скрытых значений. Ничьи: competition ranking (1,1,3), равные игровые места получают одинаковые турнирные очки; равная итоговая сумма означает совместных победителей. WinnerDetermined содержит все итоговые места; победители — строки place=1.

В источнике создание допускает указание размера команды, но регистрация строго требует четыре: принимается только TeamSize=4. Апелляция одна на задание за турнир, а не на игру: taskId должен быть стабильным идентификатором задания в разных играх, внешний checking хранит уникальность `(tournamentId,teamId,taskId)` и не сбрасывает её после закрытия. Отдельные задачи разных игр имеют разные ID. Демо использует game1-task1/game2-task1, поэтому апелляции в двух играх относятся к разным заданиям.

## Границы реализации

Сервисы team/checking не реализованы по запросу пользователя. Их аутентификация, назначения, проверка QR, хранение фотографий, лимит апелляций и права конкретного проверяющего принадлежат этим внешним сервисам, описаны в integration.md. Имитация не удостоверяет эти проверки; она проверяет интеграцию трёх реализованных сервисов.

SQLite и снимок состояния рассчитаны на небольшой турнир и один экземпляр каждой роли. Нет очистки старых receipts/outbox, метрик, OIDC, TLS, многоузлового масштабирования или операторского API исправления quarantine. Используются отдельные локальные bearer-ключи и явные тестовые значения; при развёртывании замените ACTORS и все KEY_*. В судейский интерфейс нельзя встраивать публичную таблицу или передавать team/rank. .NET 8 выбран для установленного SDK 8.0.302; для промышленной эксплуатации следует перейти на поддерживаемую .NET LTS и обновить зависимости. Docker Compose здесь не запускался: Docker отсутствует.
