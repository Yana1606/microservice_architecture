# Архитектура и трассировка требований

## 1. Назначение

Проект моделирует проведение математического турнира: создание регламента, регистрацию команд, подготовку и запуск игр, приём результатов проверки, расчёт баллов, определение мест и завершение турнира.

Архитектура разделяет ответственность между тремя основными сервисами:

- `tournament` — управление жизненным циклом турнира;
- `scores` — обработка результатов отдельных заданий;
- `results` — расчёт игровых и турнирных итогов.

`simulator` используется для воспроизведения событий внешних сервисов команд и проверок. Он не является полноценной реализацией этих сервисов.

## 2. Контекст и трассировка требований

| Процесс | Владелец и обработчик | Результат интеграции |
|---|---|---|
| Создание турнира и назначение жюри | `tournament`, `Engine.Create` | `TournamentCreated` |
| Настройка и удаление игр до старта | `tournament`, команды конфигурации | `GamesConfigured` |
| Публикация регламента | `tournament` | `TournamentPublished` |
| Регистрация команд | `tournament` | `TeamRegistered` или `RegistrationRejected` |
| Открытие турнира | `tournament` | `TournamentStarted` |
| Запуск игры | `tournament` | Saga подготовки и затем `GameStarted` |
| Закрытие сроков | `tournament`, `Tick` | `SolutionsClosed`, `AppealsClosed` |
| Завершение турнира | `tournament` | `TournamentCompleted` |
| Привязка решения к команде | внешний `team` | `SolutionBound` |
| Завершение приёма решений | внешний `team` | `TeamSealed` |
| Публикация результата проверки | внешний `checking` | `VerdictRecorded` |
| Завершение проверок | внешний `checking` | `ChecksSealed` |
| Расчёт матрицы баллов | `scores` | `InitialResultsCreated`, `ScoreChanged` |
| Подготовка итогов игры | `scores` и `results` | `ScoresReady`, `GameFinalized` |
| Определение победителя | `results` | `WinnerDetermined` |

Существенные зависимости:

1. `GameStarted` запускает инициализацию матрицы баллов и подготовку бланков.
2. Для окончательного расчёта необходимы закрытие обоих приёмов и полный манифест результатов проверки.
3. `GameFinalized` разрешает переход к следующей игре и фиксирует вклад команд в турнир.
4. `WinnerDetermined` приводит к завершению турнира.

## 3. Процессы и границы ответственности

| Процесс | Владеет данными | Основные обязанности |
|---|---|---|
| `tournament` | Турниры, команды, игры, сроки, Saga | Регламент, регистрация, запуск, компенсация, завершение |
| `scores` | Привязки, ячейки результатов, вердикты, снимки | Применение результатов проверки и публикация баллов |
| `results` | Итоги игр, места, турнирные очки | Подведение итогов и определение победителя |
| `simulator` | Тестовые резервы и наборы событий | Воспроизведение интеграции внешних участников |

Каждая роль запускается отдельным процессом Host с выбранной конфигурацией `SERVICE`. Роль ограничивает доступные REST-маршруты и допустимые типы событий.

У каждого процесса собственная SQLite-база и собственный Outbox. Прямое чтение или изменение базы другого сервиса не используется.

## 4. Основные агрегаты и состояния

### Турнир

Жизненный цикл:

```text
Draft → Registration → Running → Completed
```

Турнир содержит регламент, список зарегистрированных команд и упорядоченный набор игр.

Регистрация проверяет требования к составу. В текущей реализации команда должна содержать ровно четыре разных участника, а капитан должен входить в состав. Для запуска турнира требуется минимум две команды.

### Игра

Основные состояния:

```text
Configured → Preparing → Running → Completed
                 |
                 v
           Compensating
                 |
                 v
             Configured
```

Игра запускается только после успешного завершения подготовки. При отказе или тайм-ауте выполняется компенсация резервов. Пока компенсация не подтверждена всеми участниками, повторный запуск запрещён.

Сроки решений и апелляций фиксируются как абсолютные UTC-времена при успешном запуске игры.

### Результаты

`ScoreGame` содержит ячейки `Cells[team][task]`, привязки решений, вердикты и манифесты завершения.

Упрощённая модель состояний ячейки:

```text
NotSubmitted → Correct
             → Incorrect → AppealUpheld
                          → AppealRejected
```

Результат игры хранится один раз по паре `(tournamentId, gameId)`. Турнирные очки рассчитываются из уникальных вкладов игр. Повторное событие не должно повторно начислять очки.

## 5. Хранение данных

Используется SQLite в режиме WAL. Миграции SQL применяются при запуске сервиса под блокировкой.

Для учебного масштаба состояние сервиса хранится единым JSON-снимком в SQL-строке. Локальные изменения выполняются в транзакциях SQLite.

Ключевые гарантии:

- состояние, Inbox/receipts, Outbox и сохранённый ответ команды фиксируются одной локальной транзакцией;
- ошибка до `COMMIT` приводит к откату;
- `BEGIN IMMEDIATE` сериализует конкурирующие записи;
- REST-команды дополнительно используют `If-Match` и `Revision`;
- конфликт параллельных изменений возвращается как `revision_conflict`.

Каждый сервис отвечает только за собственные данные. Согласование между сервисами достигается сообщениями и повторной обработкой событий.

## 6. Идемпотентность и доставка событий

Изменяющие REST-запросы используют `Idempotency-Key`.

Повтор запроса с тем же ключом и тем же содержимым возвращает сохранённый ответ. Повторное использование ключа с другим содержимым отклоняется.

Для событий сохраняется исходный конверт. Повтор одного `eventId` с тем же содержимым безопасен; тот же ID с другим содержимым считается конфликтом.

Дополнительно применяется семантическая защита вердиктов по паре `(anonymousId, revision)`. Она предотвращает повторное начисление при повторной публикации того же решения с новым транспортным ID.

### Outbox

Исходящие события сначала записываются в локальную базу в той же транзакции, что и бизнес-изменение. Фоновый dispatcher отправляет их получателям по HTTP.

Доставка имеет семантику at least once. Получатель должен поддерживать идемпотентную обработку.

Временные ошибки:

- сетевые ошибки;
- timeout;
- HTTP 408;
- HTTP 429;
- HTTP 5xx.

Для них сохраняются попытки и время следующей доставки. Используется экспоненциальная задержка.

Постоянные HTTP 4xx, кроме 408 и 429, переводятся в Dead Letter Queue. Такие сообщения больше не блокируют следующие события тому же получателю. Организатор может просмотреть их и вручную вернуть в очередь после устранения причины.

### Inbox и отложенные события

Входящие события фиксируются вместе с изменением состояния. События, которые пока нельзя применить из-за отсутствующих зависимостей, сохраняются и рассматриваются повторно после поступления новых данных и после перезапуска.

Конфликтующие предметные события попадают в quarantine и доступны в защищённой диагностике. Автоматическое удаление таких записей не выполняется.

## 7. Saga подготовки игры

Подготовка игры нужна, чтобы зарезервировать ресурсы в нескольких независимых сервисах до фактического запуска.

Координатор Saga принадлежит `tournament`. Он сохраняет:

- `attemptId`;
- `tournamentId`;
- `gameId`;
- текущее состояние;
- шаг подготовки;
- deadline;
- причину отказа;
- состояние компенсации.

Последовательность успешной подготовки:

```text
ReserveScoreboard
    ↓
ScoreboardReserved
    ↓
ReserveForms
    ↓
FormsReserved
    ↓
GameStarted
```

Если один из участников отказывает или истекает срок подготовки:

```text
ReleaseScoreboard
ReleaseForms
    ↓
ScoreboardReleased
FormsReleased
    ↓
Configured
```

Обе компенсации отправляются независимо от того, был ли получен ответ о резервировании: участник мог успешно сохранить резерв, а ответ мог потеряться при доставке.

Каждая попытка имеет уникальный `attemptId`. Поздний ответ старой попытки не должен изменять состояние новой попытки.

Резервирование и освобождение выполняются локальными транзакциями владельцев данных. Saga не является общей транзакцией нескольких SQLite.

## 8. Сроки и фоновая обработка

`DeadlineWorker` проверяет сохранённые UTC-сроки каждые 250 мс.

После перезапуска сервиса просроченные приёмы закрываются на основании сохранённых абсолютных сроков. Уведомление о закрытии может задержаться в Outbox, поэтому внешние сервисы также обязаны проверять абсолютный срок самостоятельно.

Работа с дедлайнами не зависит от успешности сетевой доставки событий.

## 9. Барьер готовности итогов

Проверка только отсутствия активных проверок недостаточна: сообщение об отсутствии работы может прийти раньше последнего вердикта.

Поэтому используются два манифеста:

- `TeamSealed` — полный набор принятых решений;
- `ChecksSealed` — полный набор ID всех окончательных первичных и апелляционных вердиктов.

`ScoresReady` публикуется только при выполнении всех условий:

1. получены закрытия обоих приёмов;
2. все привязки из `TeamSealed` получены и лишних привязок нет;
3. каждому принятому решению соответствует первичный вердикт;
4. все вердикты из `ChecksSealed` применены;
5. отсутствуют неразрешённые pending и quarantine-события по игре.

Апелляционный вердикт `revision=2` ожидает первичный `revision=1`.

Пустая игра допустима только при наличии обоих явных пустых манифестов.

Барьер зависит от корректности внешних сервисов: преждевременный или неполный seal является нарушением интеграционного контракта.

## 10. Расчёт баллов и итогов

`Scores` хранит результаты по командам и заданиям. Изменение вердикта приводит к пересчёту соответствующей ячейки и обновлению публичной проекции.

`Results` рассчитывает игровые места и турнирные очки. Используемая в учебной демонстрации формула:

```text
points = 100 - 2 × (place - 1)
```

Применяется competition ranking: например, места `1, 1, 3`. Команды с одинаковым итоговым количеством очков могут стать совместными победителями.

Формула стоимости задания, значения модификаторов и правило ничьих не были полностью заданы исходными требованиями. Используемые демонстрационные параметры являются учебным регламентом и должны быть согласованы перед реальным турниром.

## 11. Публичная таблица и кеширование

Публичная таблица формируется из данных, предназначенных для зрителей. Приватные привязки решений, эталоны и состав жюри в неё не включаются.

Снимок таблицы хранится в `public_snapshots` с версией `revision` и JSON-представлением.

Обновление публичного снимка выполняется в той же SQLite-транзакции, что и изменение данных баллов или итогов. Версия увеличивается только при изменении публично видимого содержимого.

После `COMMIT` публикуется уведомление об инвалидации кеша.

GET и SSE используют общий `TableSnapshotCache`:

- ключ содержит ID турнира;
- TTL составляет 10 секунд;
- настроено ограничение размера кеша;
- сохраняемая версия проверяется перед возвратом кешированного значения;
- устаревший снимок не должен пережить изменение версии в базе.

Проверка версии при чтении позволяет обнаружить изменения, внесённые другим экземпляром `Store`. Это повышает актуальность, но означает дополнительное обращение к SQLite при чтении кеша.

SSE периодически получает актуальный снимок. Частота опроса влияет на нагрузку SQLite, поэтому для масштабирования потребуется отдельный механизм межпроцессных уведомлений.

## 12. CAP и eventual consistency

Проект не следует целиком классифицировать как AP или CP.

В лабораторном сценарии рассматриваются разные операции:

- чтение последнего известного публичного снимка может оставаться доступным при задержке событий;
- переход к следующей игре блокируется, пока турнир не получил подтверждённый итог предыдущей игры;
- после восстановления доставки проекции сходятся к согласованному конечному состоянию.

Сценарий показывает компромисс между доступностью чтения и строгой проверкой бизнес-переходов. Он не является формальным доказательством CAP.

## 13. Ограниченный детерминизм

Проверки детерминизма используют фиксированные входные факты, время и идентификаторы.

Сравнивается конечная публичная бизнес-проекция: баллы, статусы, места, очки и завершение турнира.

Не требуется совпадение промежуточных снимков, технических ID исходящих сообщений и аудита.

Гарантия ограничена одинаковыми непротиворечивыми фактами, корректными конечными манифестами, идемпотентностью и детерминированной формулой расчёта.

## 14. Учебная модель 2PC

`TwoPhaseLab` — отдельный консольный пример протокола двухфазной фиксации.

Координатор и два участника используют отдельные SQLite-файлы. Модель демонстрирует:

- Commit;
- Abort;
- восстановление координатора после Prepare.

Это учебная модель прикладных резервирований. Она не использует XA/DTC и не является распределённой транзакцией самой SQLite. В основной жизненный цикл турнира она не включена.

В отличие от Saga, при 2PC участник после Prepare может удерживать резерв и ожидать окончательного решения координатора. Saga допускает уже зафиксированные локальные изменения, которые затем компенсируются отдельными транзакциями.

## 15. Безопасность и приватность

Внешние сервисы команд и проверок должны быть разделены по доступу к данным.

Сервис `checking` не должен получать сведения о владельце решения или публичных местах команд. В публичную таблицу не включаются фотографии, эталоны и приватные привязки.

Для локальной интеграции используются bearer-ключи. Перед развёртыванием необходимо заменить тестовые значения ключей и конфигурации акторов.

Текущая лабораторная реализация не заявляет промышленную аутентификацию, OIDC или TLS.

## 16. Ограничения

- `team` и `checking` не реализованы как отдельные полноценные сервисы.
- `simulator` воспроизводит только часть их поведения.
- SQLite и JSON-снимок ориентированы на небольшой турнир и один экземпляр каждой роли.
- Не реализованы промышленное масштабирование, OIDC, TLS и метрики.
- Нет автоматической очистки старых receipts и Outbox.
- Предметный quarantine требует отдельного разбора.
- Учебная модель 2PC не является XA/DTC.
- CAP-сценарий моделирует задержку доставки, а не реальный сетевой раздел.
- Реальная работа QR, фотографий и судейского интерфейса относится к внешним сервисам.
