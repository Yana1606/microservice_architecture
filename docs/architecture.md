Эти связи реализованы, а не только порядок карточек слева направо.

## Агрегаты и состояния

Tournament включает регистрации и упорядоченные Game: Draft → Registration → Running → Completed. Game: Configured → Preparing → Running → Completed; отказ/тайм-аут: Preparing → Compensating → Configured; SolutionsClosed и AppealsClosed — независимые монотонные флаги, UTC-сроки сохраняются при старте. ScoreGame содержит Cells[team][task], неизменяемые Binding и Verdict, манифесты завершения. Cell: NotSubmitted → Correct/Incorrect; Incorrect → AppealUpheld/AppealRejected. GameResult хранится один раз по `(tournament,game)`. Сумма турнира всегда вычисляется из уникальных вкладов игр; операции «прибавить ещё раз» нет.

Три отдельно запускаемых процесса используют общий исполняемый Host с выбранной ролью SERVICE. Роль ограничивает маршруты REST и допустимые события; БД и outbox независимы. Общая библиотека содержит DTO, чистые обработчики и инфраструктуру; прямого доступа к чужой БД нет.

## Хранение и доставка

SQLite WAL; миграции 001–005 применяются при запуске под блокировкой. Для небольшого турнира состояние сервиса хранится одним JSON-снимком в SQL-строке. BEGIN IMMEDIATE сериализует изменения между процессами; REST дополнительно требует If-Match с Revision турнира. Гонка двух команд на одной версии даёт один успех и один revision_conflict. Состояние, receipts/inbox, pending, quarantine, outbox и результат команды фиксируются одной транзакцией. Ошибка до COMMIT откатывает всё.

Idempotency-Key обязателен для изменяющих REST-запросов; повтор того же запроса возвращает сохранённый ответ, повтор ключа с другим содержимым отклоняется. Для событий сохраняется исходный конверт; одинаковый event ID с другим содержимым отклоняется. Семантический ключ вердикта `(anonymousId,revision)` защищает от двойного начисления даже с новым event ID.

HTTP-доставка at least once: строка outbox отмечается sent только после успешного ответа. Потеря ответа после COMMIT получателя приводит к безопасному повтору. Временные ошибки (сеть, timeout, HTTP 408/429/5xx) сохраняют attempts/last_error и получают экспоненциальную задержку; сетевой сбой или временный HTTP-ответ останавливает текущую пачку этого получателя. Постоянные HTTP 4xx, кроме 408 и 429, переводятся в durable dead-letter с кодом ответа и временем: они исключаются из очереди и не блокируют последующие события тому же получателю. Защищённые организатором GET /internal/outbox/dead-letter и POST /internal/outbox/dead-letter/{eventId}/{destination}/retry позволяют проверить причину и вручную вернуть запись в очередь после устранения проблемы. Попытки сохраняются, повторный запуск не теряет исходное событие. Pending сообщения с неизвестным турниром, не начатой игрой, неизвестной связью или недоставленным первичным вердиктом сохраняются и повторно рассматриваются при каждом событии и после перезапуска. Конфликтующие предметные события попадают в quarantine; это видно в защищённой диагностике. Автоматического удаления таких событий нет.

Независимый DeadlineWorker проверяет сохранённые UTC-сроки каждые 250 мс, при перезапуске закрывает просроченные приёмы. Получатели team/checking должны проверять сам абсолютный срок, а не ждать доставки уведомления закрытия. Уведомление может задержаться. Доставка работает в отдельном цикле и не блокирует проверку сроков. При сетевом сбое само уведомление придёт позднее; право подачи определяется сохранённым абсолютным сроком.

## Барьер итогов

Одного события «нет активных проверок» недостаточно: оно может обогнать вердикт. TeamSealed после закрытия решений содержит полный набор anonymousId принятых решений. ChecksSealed после закрытия обоих приёмов содержит полный набор **event ID всех** первичных и апелляционных вердиктов. Это контракт конечности потока, который внешний checking выдаёт только после завершения всех назначений, отказов и перепроверок, согласовав полный набор решений с team.

ScoresReady публикуется только когда: оба закрытия доставлены; все Binding из TeamSealed есть и лишних нет; каждому решению соответствует первичный вердикт; все и только вердикты из ChecksSealed применены; нет pending и quarantine по игре. Апелляционный вердикт revision=2 ждёт revision=1. Пустая игра разрешена только при двух явных пустых манифестах. Приём итогов results дополнительно ждёт оба закрытия и проверяет полный набор команд. Барьер является доверенным утверждением внешних сервисов; ранний или ложный seal нарушает их контракт. Сообщения сверх финального seal не меняют запечатанный результат, а становятся инцидентом интеграции.

## Решения по отсутствующим правилам

Исходные источники не задают формулу баллов задач, значения модификаторов и правило ничьих. Подтверждение отдельного согласования этих правил в репозитории отсутствует. Для существующей учебной демонстрации используются: `баллы = стоимость исхода × множитель бланка`; обычный ×1, усиленный ×1.5, рискованный ×2; демо верно=10, неверно=0. Сами стоимости и множители обязательны в GameConfig, нет скрытых значений. Эти настройки и единственная поддерживаемая политика SharedCompetition являются демонстрационным регламентом, а не восстановленными требованиями источников. Для реального турнира организатор должен согласовать формулу, значения и правило ничьих до публикации; произвольный текст регламента не меняет алгоритм. Ничьи: competition ranking (1,1,3), равные игровые места получают одинаковые турнирные очки; равная итоговая сумма означает совместных победителей. WinnerDetermined содержит все итоговые места; победители — строки place=1.

В источнике создание допускает указание размера команды, но регистрация строго требует четыре: принимается только TeamSize=4. Апелляция одна на задание за турнир, а не на игру: taskId должен быть стабильным идентификатором задания в разных играх, внешний checking хранит уникальность `(tournamentId,teamId,taskId)` и не сбрасывает её после закрытия. Отдельные задачи разных игр имеют разные ID. Демо использует game1-task1/game2-task1, поэтому апелляции в двух играх относятся к разным заданиям.

## Границы реализации

Сервисы team/checking не реализованы по запросу пользователя. Их аутентификация, назначения, проверка QR, хранение фотографий, лимит апелляций и права конкретного проверяющего принадлежат этим внешним сервисам, описаны в integration.md. Имитация не удостоверяет эти проверки; она проверяет интеграцию трёх реализованных сервисов.

SQLite и снимок состояния рассчитаны на небольшой турнир и один экземпляр каждой роли. Нет очистки старых receipts/outbox, метрик, OIDC, TLS или многоузлового масштабирования. Dead-letter outbox имеет ручное восстановление; предметный quarantine входящих событий по-прежнему требует отдельного разбора. Используются отдельные локальные bearer-ключи и явные тестовые значения; при развёртывании замените ACTORS и все KEY_*. В судейский интерфейс нельзя встраивать публичную таблицу или передавать team/rank. .NET 8 выбран для установленного SDK 8.0.302; для промышленной эксплуатации следует перейти на поддерживаемую .NET LTS и обновить зависимости. Docker Compose здесь не запускался: Docker отсутствует.


## Saga подготовки и владельцы данных

Турнир владеет `GamePreparation` (attemptId, tournamentId, gameId, status, step, deadline, failure, released) в своей SQLite. Команда start-game создаёт попытку, а не немедленно начинает игру. Подготовка длится не более 15 секунд до решения; сроки решения/апелляции устанавливаются только при успехе. Баллы владеют `PreparationReservation` таблицы, имитатор — `PreparationReservation` комплектов бланков для перечисленных команд. Это локальные сохраняемые резервы, не публичные результаты и не выданные командам бланки.

ReserveScoreboard → ScoreboardReserved → ReserveForms → FormsReserved → GameStarted. Отказ или тайм-аут → ReleaseScoreboard и ReleaseForms → ScoreboardReleased и FormsReleased → Configured. Обе компенсации отправляются всегда: локальное резервирование могло закоммититься без доставленного ответа. Освобождение действительно переводит резерв в Released; записи-тумбстоуны сохраняются, поэтому запоздалый Reserve старой попытки не восстанавливает резерв. Activated не отменяется поздней командой освобождения. Все переходы, inbox и outbox фиксируются локальной транзакцией. Новая попытка получает новый attemptId; старые подтверждения не участвуют в её решении.

## Доставка и публичный кеш

Выборка outbox ограничивается отдельно для каждого получателя; получатели обслуживаются параллельно, внутри группы — последовательно. Ошибка не исключает сообщение из очереди; next_attempt_ms и экспоненциальная задержка 1–60 секунд сохраняются миграцией 002. Диагностика считает все ожидающие сообщения, а не размер очередной пачки.

Миграция 003 хранит public_snapshots(tournament_id, revision, json). В той же транзакции, что изменение баллов/итогов, обновляются публичный JSON и его версия, только если видимые данные изменились. После COMMIT вызывается инвалидация IMemoryCache. GET/SSE используют один TableSnapshotCache, TTL 10 секунд, ограничение размера 2048 записей. Проверка сохраняемой версии защищает от устаревшего заполнения после инвалидации, в том числе при записи другим экземпляром Store. В кеш не попадают приватные привязки решений, эталоны и состав жюри.

## Учебные сценарии

[defense.md](defense.md) содержит команды и смысл каждого показа. CAP обсуждается по операциям чтения снимка и допуска следующей игры; общий ярлык AP/CP проекту не назначается. Детерминизм проверяет одинаковую конечную бизнес-проекцию при 32 допустимых порядках фиксированных фактов; технические IDs исходящих сообщений не сравниваются. Пример 2PC запускается отдельно, использует три собственных SQLite и не включён в жизненный цикл турнира. Это модель прикладных резервов, а не XA или встроенный распределённый коммит SQLite.
