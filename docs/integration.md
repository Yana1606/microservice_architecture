# Контракт интеграции внешних сервисов

## 1. Назначение

Документ описывает взаимодействие микросервисов турнира и контракты внешних участников.

Основные сервисы:

- `tournament`;
- `scores`;
- `results`.

`simulator` воспроизводит часть поведения внешних сервисов `team` и `checking` для лабораторной демонстрации. Он не является их полноценной реализацией.

Контракт событий версии v1 описан в OpenAPI и `Contracts.cs`.

## 2. Общие правила событий

Каждое событие передаётся в конверте Event v1.

Основные поля:

- `eventId` — UUID без дефисов, неизменяемый при транспортном повторе;
- `type` — тип события;
- `version` — версия контракта;
- `producer` — отправитель;
- `correlationId` — идентификатор турнира;
- `causationId` — идентификатор команды или события, вызвавшего публикацию;
- `occurredAt` — время возникновения события в UTC;
- `payload` — данные события.

`occurredAt` используется для аудита, а не для определения порядка применения событий.

Producer должен использовать соответствующий bearer-ключ. Сервис проверяет разрешённую пару отправителя и типа события.

Неизвестная версия контракта отклоняется с `unsupported_event`. Несовместимое изменение следует публиковать с новой версией и отдельным обработчиком.

Повтор события с тем же ID и содержимым должен обрабатываться идемпотентно. Тот же ID с другим содержимым считается конфликтом.

## 3. Основные события и маршрутизация

| Отправитель | Событие | Получатели | Назначение |
|---|---|---|---|
| `tournament` | `TournamentStarted` | `team`/`simulator`, `scores`, `results` | Открытие турнира и подготовка данных |
| `tournament` | `GameStarted` | `team`/`simulator`, `scores`, `results` | Запуск игры |
| `tournament` | `SolutionsClosed` | `team`/`simulator`, `scores`, `results` | Закрытие приёма решений |
| `tournament` | `AppealsClosed` | `team`/`simulator`, `scores`, `results` | Закрытие приёма апелляций |
| `team` | `SolutionBound` | `scores` | Привязка анонимного решения к команде |
| `team` | `TeamSealed` | `scores` | Полный манифест принятых решений |
| `checking` | `VerdictRecorded` | `scores` | Результат проверки |
| `checking` | `ChecksSealed` | `scores` | Полный манифест окончательных вердиктов |
| `scores` | `ScoresReady` | `results` | Подтверждение готовности баллов |
| `results` | `GameFinalized` | `tournament`, `scores`, `simulator` | Итог игры |
| `results` | `WinnerDetermined` | `tournament`, `scores`, `simulator` | Итоговые места турнира |

В тестовой конфигурации часть внешних получателей заменена `simulator`. Это не меняет требований к контрактам реальных `team` и `checking`.

Дополнительные события жизненного цикла и подготовки игры описаны ниже.

## 4. Идентификаторы игры и миграция ключей

Внешние `tournamentId` и `gameId` остаются неизменными.

Внутренний составной ключ игры формируется с экранированием каждой части через `Uri.EscapeDataString` перед соединением символом `/`.

Это необходимо, чтобы различать пары:

```text
tournamentId = cup/x
gameId       = round
```

и

```text
tournamentId = cup
gameId       = x/round
```

Символ `%` также экранируется. Поэтому литеральная последовательность `%2F` не совпадает с закодированным `/`.

Миграция 004 переводит старые ключи в `Scores`, `Finals` и `Snapshots` на новый формат по сохранённым конфигурациям турниров.

Миграция должна сохранять результаты, receipts, Outbox и сохранённые ответы команд. Повторное открытие базы не должно повторно изменять уже мигрированные данные.

Если старый ключ имеет неоднозначного владельца, миграция завершается ошибкой `ambiguous_legacy_game_key` и откатывает транзакцию. Выбирать владельца автоматически запрещено.

## 5. Приватность и разделение данных

Данные команд и проверок должны быть разделены.

`AnonymousReview` передаётся по приватному каналу `team → checking` и может содержать:

- `anonymousId`;
- `taskId`;
- `photoUrl`;
- `statement`;
- `reference`;
- `assignedJury`;
- `appeal`;
- `reason`.

QR содержит только случайный номер бланка.

Сервис `team` хранит соответствие владельца и анонимного идентификатора. Сервис `checking` не должен получать владельца решения, сведения о команде и её место в таблице.

Фотографии необходимо очищать от идентификаторов и метаданных до передачи проверяющему.

Фото, условия, эталоны и состав жюри не публикуются в публичной таблице и публичном REST API.

Организаторские маршруты конфигурации должны быть защищены.

## 6. Обязанности сервиса team

Полноценный сервис `team` в рамках проекта не реализован. Ниже описан контракт, который должен выполнять внешний участник.

### Подготовка бланков

После `TournamentStarted` сервис готовит бланки для игр турнира.

После `GameStarted` он активирует комплект для конкретной игры.

### Приём решений

Приём фотографии должен проверять в одной транзакции:

- абсолютный UTC-срок;
- принадлежность бланка команде;
- факт выдачи бланка;
- отсутствие предыдущей успешной сдачи;
- корректность QR;
- наличие фотографии.

Возможные причины отказа:

```text
solutions_closed
form_not_owned
form_not_issued
form_already_submitted
invalid_qr
photo_required
```

Отклонённые фотографии не должны передаваться в `checking`.

Успешная сдача атомарно создаёт:

- `SolutionBound` для `scores`;
- приватный `AnonymousReview` для `checking`.

### Завершение приёма

После закрытия приёма и завершения обработки принятых решений сервис публикует `TeamSealed`.

В манифест включаются все `anonymousId` принятых решений игры. Нельзя публиковать неполный манифест.

### Вопросы и следующие задания

Выдача следующего задания зависит от правил конкретного типа игры. Реализованные сервисы турнира, баллов и итогов не определяют эти правила.

Вопрос допускается только во время игры и по уже выданному заданию. Ответ должен быть связан с существующим вопросом и доступен его автору. Вопрос проверяющему остаётся анонимным.

## 7. Обязанности сервиса checking

Полноценный сервис `checking` в рамках проекта не реализован. Описанный ниже контракт определяет ожидаемое поведение внешней системы.

### Назначение проверяющего

Решение ожидает свободного члена жюри и назначается ровно одному проверяющему.

Принятие вердикта возможно только при совпадении назначенного `juryId`.

### Первичная проверка

Допустимые исходы:

```text
correct
incorrect
refuse
```

`refuse` не считается неверным решением и не начисляет баллы. Отказ требует эскалации старшему проверяющему.

Окончательный первичный вердикт публикуется как `VerdictRecorded` с `revision=1`.

Обычное решение имеет `Authority=Jury`, решение старшего — `Authority=Senior`.

Эскалация и назначение остаются внутренними событиями сервиса checking, например:

```text
ReviewAssigned
ReviewRefused
ReviewEscalated
```

В `scores` передаётся только окончательный результат этапа проверки.

### Апелляция

Апелляция допускается, если:

- первичный результат — `Incorrect`;
- указано непустое обоснование;
- текущее время меньше `AppealsDue`;
- ранее не подавалась апелляция по этому заданию в данном турнире.

Ограничение хранится по ключу:

```text
(tournamentId, teamId, taskId)
```

Оно действует между разными играми и после закрытия отдельных окон. `taskId` должен быть стабильным идентификатором задания.

Причины отказа:

```text
task_not_incorrect
appeal_deadline_expired
appeal_already_used
reason_required
not_team_captain
```

Принятая апелляция создаёт одну анонимную перепроверку другим членом жюри. Ему передаются `appeal=true`, фото, условие, эталон и обоснование.

Если проверяющий отказывается от апелляции, она эскалируется старшему.

Результат апелляции публикуется как `VerdictRecorded` с `revision=2`:

```text
AppealUpheld
AppealRejected
```

Повторное обращение не создаёт `revision=3`. Конфликтующие финальные вердикты считаются ошибкой интеграции.

## 8. Манифест завершения проверок

`ChecksSealed` публикуется только после:

1. закрытия обоих приёмов;
2. получения полного `TeamSealed`;
3. завершения каждой первичной проверки;
4. завершения каждой поданной апелляции;
5. завершения всех эскалаций старшему проверяющему.

В `ChecksSealed` включаются ID всех опубликованных окончательных `VerdictRecorded`, включая первичные и апелляционные.

После публикации seal запрещено создавать новые принятые решения, апелляции и вердикты.

Нельзя определять готовность только по пустому списку активных проверок: система должна знать полный манифест принятых решений от `team`.

## 9. Контракт подготовки игры v1

Подготовка игры реализуется через локальные резервы участников и координатор Saga в `tournament`.

| Команда или событие | Отправитель → получатель | Payload |
|---|---|---|
| `ReserveScoreboard` | `tournament` → `scores` | `PreparationRequest(attemptId, config, teamIds)` |
| `ScoreboardReserved` | `scores` → `tournament` | `PreparationReply(attemptId)` |
| `ScoreboardPreparationRejected` | `scores` → `tournament` | `PreparationReply(attemptId, reason)` |
| `ReserveForms` | `tournament` → `simulator` | `PreparationRequest` |
| `FormsReserved` | `simulator` → `tournament` | `PreparationReply` |
| `FormsPreparationRejected` | `simulator` → `tournament` | `PreparationReply` |
| `ReleaseScoreboard` | `tournament` → `scores` | `PreparationReply` |
| `ReleaseForms` | `tournament` → `simulator` | `PreparationReply` |
| `ScoreboardReleased` | `scores` → `tournament` | `PreparationReply` |
| `FormsReleased` | `simulator` → `tournament` | `PreparationReply` |
| `GameStarted` | `tournament` → участники | `Game`, `preparationAttemptId`, абсолютные сроки |

`attemptId` идентифицирует попытку подготовки. `causationId` связывает ответ с командой, вызвавшей его.

ID конверта не меняется при транспортном повторе.

Баллы и имитатор резервируют только собственные данные. Резерв не создаёт активных ячеек публичной таблицы и не означает выдачу бланков командам.

После `GameStarted` резерв становится активным. Состояние `Released` сохраняется как запрет повторного резервирования той же попытки.

Поздний ответ старой попытки после компенсации или успешного запуска не должен менять новую попытку.

До получения обоих подтверждений освобождения координатор не разрешает повторный запуск.

## 10. Контракт имитатора

Тестовый маршрут:

```text
POST /fixtures/{tournament}/{game}
```

Использует отдельный bearer-ключ:

```text
simulator-demo
```

Имитатор создаёт сохраняемый набор привязок, вердиктов и seal-событий. Он может отправлять события в обратном порядке и повторно использовать те же ID при повторном вызове.

Это исключительно тестовый API. Он не является интерфейсом судьи и не подтверждает реальную проверку QR, фотографий, прав доступа или подачи апелляции.

OpenAPI v1 допускает `simulator` как producer ответов Saga:

- `FormsReserved`;
- `FormsReleased`;
- `FormsPreparationRejected`.

Разрешённые пары producer/type/version проверяются принимающим сервисом.

## 11. Управляемые лабораторные сбои

Управляющие маршруты доступны только при включённом `ENABLE_LAB_DEMOS=1`.

Примеры:

- `POST /lab/reject-next-forms` — имитатор отклоняет следующее резервирование бланков;
- `POST /lab/delivery/{destination}/pause` — приостанавливает доставку выбранному получателю;
- `POST /lab/delivery/{destination}/resume` — возобновляет доставку;
- `GET /lab/reservations` — показывает тестовые резервы имитатора.

Маршруты защищены соответствующими ключами организатора или `SIMULATOR_KEY`.

Пауза означает удержание событий в Outbox. Она не выключает сервис и не подменяет его результаты.

При прямом запуске Host без `ENABLE_LAB_DEMOS=1` управляющие маршруты должны возвращать 404.

## 12. Восстановление Outbox

Постоянные HTTP 4xx, кроме 408 и 429, переводятся в Dead Letter Queue.

Организатор может запросить список:

```http
GET /internal/outbox/dead-letter
```

После устранения причины сообщение можно вернуть в очередь:

```http
POST /internal/outbox/dead-letter/{eventId}/{destination}/retry
```

Временные ошибки — сеть, timeout, HTTP 408, 429 и 5xx — повторяются автоматически с задержкой.

Маршруты требуют bearer-токен организатора.

## 13. Требования к реальной интеграции

Перед подключением полноценных `team` и `checking` необходимо:

1. Согласовать версию и схему каждого события.
2. Настроить отдельные ключи producer.
3. Реализовать Inbox и идемпотентную обработку.
4. Обеспечить атомарность локального изменения и записи исходящих событий.
5. Реализовать полные манифесты `TeamSealed` и `ChecksSealed`.
6. Проверять абсолютные UTC-сроки независимо от доставки уведомлений.
7. Не передавать приватные сведения в публичные API.
8. Обеспечить повторную доставку и обработку поздних событий.
9. Проверить контракты на несовместимые версии и некорректные манифесты.

До выполнения этих условий `simulator` следует рассматривать только как средство интеграционного тестирования.
